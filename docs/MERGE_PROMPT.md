# MERGE_PROMPT — 통합(AI) 복기본 생성 지시문 (P4-1e)

두 교재의 복기(김종수 `kim.json`, 황변 `hwang.json`)를 세트마다 하나의 통합 복기본 `merged.json`으로 만드는 작업의 지시문. GPT(Codex 등 상위 모델)에게 그대로 준다. 작업 위치는 main 작업 트리(아래 "실행 방법"). 규칙의 근거는 `docs/INGEST.md` §2-E, 데이터 구조는 `docs/DATA.md` §1·§1.1.

---

## 프롬프트 (여기부터 모델에게 준다)

당신은 서울대학교 법학전문대학원 면접 기출 복기 자료를 통합하는 편집자다. 저장소 규칙은 `AGENTS.md`를 따른다(빌드 도구·외부 라이브러리 금지, 문서·주석 한국어, 한 항목 = 한 커밋). 이 작업은 `BUILD_PLAN.md` **P4-1e**다.

### 1. 대상과 입력

- 대상: `data/sets/<set id>/`에 `kim.json`과 `hwang.json`이 **둘 다** 있는 세트(2021~2025학년도 13세트). `kim.json`만 있는 세트(2019·2020)는 건드리지 않는다.
- 입력 파일(둘 다 교재 복기 원문이며 **수정 금지**):
  - `meta.json` — 세트 공통 필드. `{ id, school, year, name, session, track, instruction, format, themes, tags, variant, tree? }`
  - `kim.json`, `hwang.json` — 복기본. `{ label, source: { book, pages }, passages: [{ no, label, kind, length, text, source, notes }], followups: [{ student, label, items: [{ label, text, note }] }], common: [...], refs?: [...], notes?: [...] }`
  - `passages[].text`는 문단을 `\n`으로 나눈 원문. `passages[].notes`는 복기자가 원문을 설명한 문장(원문이 아님). `items[].note`가 "병기"이면 한 항목에 두 질문이 `/`로 묶여 있고, "괄호 주석"이면 질문 안에 복기자의 괄호 설명이 있다.
- 두 복기의 성격: 황변은 더 길고 매끈하게 복원한 세트가 많지만 어떤 세트는 요약(2024 오전·오후, 제시문당 3~5줄)이거나 현대어 풀이(2021 오전 제시문 2, 서유견문)다. 김종수는 원문 문체를 살린 전문이 많다. 겹치는 13세트는 두 책 모두 제시문 4개이고 순서가 같다.

### 2. 출력: `data/sets/<set id>/merged.json`

```json
{
  "label": "통합(AI)",
  "basis": ["kim", "hwang"],
  "source": { "book": "김종수 3권 기출편 + 황변 1권 복기 통합", "pages": "kim 259-261; hwang 327-328" },
  "passages": [ { "no": 1, "label": null, "kind": "prose", "length": "A4 1/2 분량", "text": "…", "source": "출처1; 출처2", "notes": ["골자 hwang. kim에만 있던 문장 2개 삽입(2·5문단)"] } ],
  "followups": [ …kim.json의 followups 그대로…, { "student": "황변", "label": "황변 복기 질문", "items": [ { "label": null, "text": "…", "note": null } ] } ],
  "common": [ …kim.json의 common 그대로… ],
  "notes": [ "질문: 황변 11문 중 7문은 김종수 묶음과 뜻이 같아 제외(목록: …)", "제시문 3: 황변=요약이라 kim 전문 사용" ]
}
```

### 3. 제시문 통합 규칙

1. 두 변형이 **같은 글의 더/덜 완전한 복원**이면: 더 긴 쪽을 골자로 삼고, 다른 쪽에만 있는 문장·정보(출처, 분량, 빠진 문장)를 알맞은 자리에 끼워 넣는다. 표현만 다르고 뜻이 같은 문장은 한쪽만 쓴다. 문단 구분은 골자 쪽을 따른다.
2. 한쪽이 다른 쪽의 **요약이거나 현대어 풀이**이면: 문장을 섞지 않는다. 전문 쪽을 통째로 쓰고 출처·분량만 보탠다. `notes`에 "hwang=요약" 또는 "hwang=현대어 풀이"라고 적는다.
3. **두 복기 모두에 없는 내용은 한 글자도 쓰지 않는다.** 문장을 매끄럽게 다듬거나 접속어를 넣지 않는다. 오탈자도 원문대로 둔다(단, 두 복기가 다른 글자를 쓰면 더 많은 쪽·더 그럴듯한 쪽을 고르고 `notes`에 적는다).
4. `source`는 두 변형의 합집합(`; `로 잇기, 같은 출처는 하나). `length`는 둘 다 있으면 황변, 아니면 있는 쪽, 없으면 `null`. `label`·`kind`는 두 변형이 같아야 하며 다르면 중단하고 보고한다. 복기자 설명(`notes`)과 `(중략)` 안쪽 생략 표시는 통합 본문에 넣지 않는다(`(중략)` 표시 자체는 원문이 둘 다 가지고 있을 때만 둔다).
5. 제시문마다 `notes`에 통합 판단을 한 줄로 기록한다: 골자(kim/hwang), 삽입한 문장 수와 위치, 요약 판정.

### 4. 질문 통합 규칙

1. `kim.json`의 `followups` 묶음은 **문장·순서·개수 그대로** 복사한다(기존 문답 기록의 키가 같은 질문을 가리켜야 한다). `common`도 그대로.
2. `hwang.json`의 질문 가운데 김종수 묶음 어디에도 **뜻이 같은 질문이 없는 것만** `{ "student": "황변", "label": "황변 복기 질문", "items": [...] }` 묶음으로 뒤에 붙인다. 뜻이 같은지의 기준: 묻는 제시문과 요구(요약·비교·입장·반박·적용)가 같으면 같은 질문이다. 표현 차이·존댓말 차이는 무시한다.
3. `note: "병기"`인 황변 항목은 두 질문으로 나눈다. 괄호 주석은 원문대로 둔다. 질문 문장은 바꾸지 않는다(제시문 참조 표기 `제시문 1〉`은 `<제시문 1>`로 통일해도 된다. `DATA.md` 규칙 4).
4. `notes`에 제외한 황변 질문과 그에 대응하는 김종수 질문 쌍을 적는다.

### 5. 검증 (반드시 수행하고 결과를 보고)

세트마다 세 가지를 따로 점검한다. 하나라도 걸리면 고친 뒤 다시 점검한다.

- (가) **날조 없음**: 통합 제시문의 모든 문장이 `kim.json` 또는 `hwang.json`의 문장(또는 둘의 결합)에 실제로 있는가. 없는 문장·구절이 하나라도 있으면 실패.
- (나) **누락 없음**: 골자로 삼지 않은 변형에만 있던 문장·정보가 빠지지 않았는가(요약·풀이로 판정한 변형은 제외). 질문이 김종수 전부 + 황변 고유 질문인가.
- (다) **일관성**: 한 편의 글로 읽히는가(같은 내용이 두 번 나오지 않는가, 문단 번호·순서가 맞는가), `label`·`kind`·제시문 수가 두 변형과 같은가.

점검은 한 번에 하지 말고, 생성과 다른 대화(또는 다른 모델 호출)에서 (가)(나)(다)를 각각 질문하는 편이 낫다. 점검 결과는 `work/reports/merge-<set id>.md`에 남긴다(`work/`는 git 무시).

### 6. 반영과 검증 명령

1. 세트의 `meta.json`에서 `"variant": "kim"`을 `"variant": "merged"`로 바꾼다(통합본이 기본 복기본이 된다).
2. 생성·검증:

```bash
node tools/build_questions.js
```

```bash
node tools/validate-data.js
```

```bash
npm test
```

3. 브라우저 확인: `npx -y serve -l 5173 .` 뒤 `http://localhost:5173/db#<set id>`에서 복기본 seg의 "통합(AI)"가 눌리고 제시문·질문이 나오는지, 모의면접 3단계의 AI 입력 미리 보기에 통합 제시문이 들어가는지.
4. 커밋: 세트 몇 개씩 묶어 `P4-1e 통합본 snu-2025-A·B·C` 형식. `data/sets/<id>/merged.json`과 `meta.json`만 커밋한다. `data/questions.js`는 생성 결과를 같은 커밋에 넣는다. `work/`는 커밋하지 않는다.
5. 13세트가 끝나면 `BUILD_PLAN.md` P4-1e를 `[x]`로 바꾸고 `DECISIONS.md` 결정 표에 한 줄(통합 기준에서 내린 판단이 있으면) 적는다.

### 7. 하지 말 것

- `kim.json`·`hwang.json`·`data/questions.js`를 직접 고치지 않는다(생성 파일·원문).
- 두 복기에 없는 문장을 만들거나, 문장을 다듬거나, 질문을 재배열·재표현하지 않는다.
- `themes`·`tags`·`instruction`·`tree`는 바꾸지 않는다. 틀렸다고 보이면 `notes`에 적고 보고한다.
- 외부 라이브러리·빌드 도구를 추가하지 않는다. 설명문·안내문·이모지를 데이터나 UI에 넣지 않는다.

### 8. 보고 형식

세트마다 한 줄: `snu-2025-A — 제시문 4(골자 h/h/k/h, 삽입 3문장), 질문 kim 17 + 황변 고유 4, 검증 가/나/다 통과, 커밋 <hash>`. 중단한 세트가 있으면 이유를 적는다.
